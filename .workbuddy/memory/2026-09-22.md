## 协议 v1 → v2 迁移（起因：玩家可以自己输入名字）

用户拍板「① 玩家可以自己输入名字 ② 同意用最小的版本验证框架」。名字要传变长字符串，
且「房间已满」需要下行通道，定长单包结构不够用 —— 协议升级。

- **新增 `screen/scripts/net/net_protocol.gd`**（`class_name NetProtocol`），**删除 `motion_packet.gd`**（v1）。
  10 字节公共头：`magic(u8) / version(u8) / type(u8) / pad(u8) / player_id(u16) / seq(u32)`，小端。
  四种包：`TYPE_DATA 0`（头+gyro3f+accel3f+buttons u16+ts u32 = 40B）、`TYPE_HELLO 1`（头+name_len u8+name utf8≤24B）、
  `TYPE_BYE 2`（头，10B）、`TYPE_FULL 128`（下行，头）。`VERSION = 2`。
- **修掉一个隐患**：`encode_hello` 原本按**字节**截断到 24B —— 一个汉字 3 字节，从中间切开会产生非法 UTF-8，
  对面 `get_string_from_utf8()` 出来就是乱码尾巴。改成 `_fit_name()` 按**字符**回退。
- `udp_server.gd`：按包类型路由（HELLO 写名字 / BYE 立即下线 / DATA 走原路）。
  - 新增 `max_players`（架构硬上限），超限回 `encode_full()`，并 emit `room_full`。
  - 未握手直接发 DATA 的宽容接入（补默认名字），少了 HELLO 也不至于让链路哑掉。
  - **加 `REJECT_COOLDOWN_MS = 2000` 冷却**：被拒的手机还在闷头发包，不加冷却就是
    「它发多少我回多少」——初测刷出 120 次/秒的日志垃圾。
- `simulator.gd`：开局发 HELLO、退出在 `_exit_tree()` 发 BYE；绑本地端口收 FULL 回包（这才测得出来）；
  收到 FULL 后 `FULL_BACKOFF = 3s` 静默再重试握手。加 `--name= / --pid= / --host= / --period=` 命令行覆盖。
- `player_session.gd`：加 `player_name`、`slot`、`display_name()`。

**验证（全部 headless 实测）**：
- 单进程 12s：969 包、0 丢、0 异常、5 次挥动，HELLO 名字正确显示。
- 满员（上限压 3 塞 5 个模拟器）：前 3 人进，后 2 人收到「房间已满」；退避生效后拒绝日志降到 3 秒一轮。
- 双进程：HELLO 带名字接入 + BYE 主动退出（不用等 3 秒超时）→ 日志 `[net] 玩家 1 主动退出`。

## 框架 core + 第一个玩法《拔河》

- **`scripts/core/minigame.gd`** —— `MiniGame` 契约：`meta()`（id/name/desc/min_players/max_players/inputs）
  + 生命周期 `setup() → countdown(t) → tick(delta) → is_over() → result()` + `status_text()`。
  框架承担公共能力（槽位/颜色/HUD/倒计时/结算），小游戏只填自己的规则。
- **`scripts/core/player_palette.gd`** —— 8 色槽位表，挑色标准是「客厅距离上互相分得开」。
- **`scripts/core/game_registry.gd`** —— 注册表，**加新玩法只改这一个文件**（`SCRIPTS` 常量数组）。
- **`scripts/core/game_flow.gd`** —— 状态机 `LOBBY → COUNTDOWN → PLAYING → RESULT → LOBBY`。
  **槽位在开局那一刻才分配**（`session.slot = 下标`），网络会话与游戏角色彻底解耦。
  `drop_player()` 用**置空而非删除**槽位 —— 抽掉中间一个会让后面所有人槽位号前移，颜色身份全乱。
- **`scripts/minigames/tug/tug_of_war.gd`** —— 拔河：偶数槽位左队、奇数右队；挥动 = 猛拉，持续倾斜 = 慢慢蹭；
  拉到 ±1 出线，40 秒到点看谁占优。`accepts_count` 只认 2 或 4 人（必须均分两队）——
  这就是「玩法人数区间 ≠ 架构上限 8」的活例子。
- `main.gd` 改造成「壳」：搭视图 + 起网络层 + 起状态机 + 显示，**零游戏规则**。
  3D 视图加了绳子和绳结（绳结位置 = 绳子偏移），大厅里绳结跟着第一个玩家的倾斜动，兼作链路指示灯。
  新增调试参数：`--sim-players=N`、`--max-players=N`、`--autostart=<id>`。

### 自检抓出的真 bug（值得记）

**`session.events` 覆盖式赋值 + 每帧读取 = 同一事件被重复计数。**
无头模式没有垂直同步，帧率远高于手机的 60Hz 发包率（实测约 200fps）——
一次挥动产生的事件会在好几帧里一直躺在 `events` 里，谁直接读就把它算好几次。
集成测试里表现为「两队拉拽次数几乎一样、且都高于各自挥动频率」（0.80/s 和 0.55/s 的挥动，
却各拉出 ~1.13/s）。

修法：`events` 改成**队列**（`push_event()` 入队，`PlayerSession.MAX_PENDING_EVENTS = 8` 封顶），
消费方用 **`drain_events()` 取走即清空**，语义钉死为「自上次 tick 以来发生的事件」。
玩法开局时再 `drain` 一次，防止大厅/倒计时期间攒下的事件在开局瞬间一起炸出来。

修完后集成实测：左队 11 拉/14 秒 = 0.79/s、右队 8 拉/14 秒 = 0.57/s，与滤波层的 0.80 / 0.55 精确吻合。
**这是给所有玩法的通用教训：任何「每帧读一次、由别处覆写」的状态，都要么取走即清空，要么用帧号去重。**

排查过程：先用一次性探针（`tools/_probe.gd`，用完已删）复刻模拟器波形单独喂 `MotionFilter`，
数出 1.2s 周期 → 0.80 次/秒、1.8s → 0.55、3.0s → 0.30，证明**滤波层本身没问题**，问题在消费端。

## 奖励接口：看广告 / 答题得道具、复活（核心新功能）

需求原话：「新增看广告得道具或复活接口，广告我单独些程序，用来答题，这样就做到了边玩边学了」。
→ 落地成一个**可替换的奖励网关**：大屏不关心奖励来自广告、答题还是家长审批，只认「给 / 不给」。

**链路**：玩法 `pending_reward_request()` → GameFlow 挂起对局（新状态 `REWARD`）→ `RewardService.request()`
→ 网关（mock / http）→ 回来 `apply_reward(req, granted, data)` → 回 PLAYING 或走 RESULT。

新增文件：
- `core/gateways/reward_gateway.gd` 基类（`begin()` / `cancel()` / `answered` 信号 / `describe()`）
- `core/gateways/mock_gateway.gd` 开发用：`policy` = grant/deny/alternate/timeout，`answer_delay_sec`
- `core/gateways/http_gateway.gd` **接用户自己的答题程序**：`POST {base}/reward/open` → `{"ticket"}` 或
  `{"granted","detail"}`；`GET {base}/reward/poll?ticket=` → `pending|granted|denied`；
  `POST {base}/reward/cancel?request_id=`
- `core/reward_service.gd` 转发 + 超时兜底（默认 45s）+ 撤单
- `tools/reward_server.py`（仓库根）**答题服务参考实现**，零依赖标准库，带手机可点的答题网页；
  题库在文件头 `QUESTION_BANK = (题干, [选项], 正确项下标)` —— 「边玩边学」的学就落在这
- `docs/reward-api.md` 接口契约（交付给用户写自己程序用）

改动：`MiniGame` 加 4 个钩子；`GameFlow` 加 `REWARD` 状态；`TugOfWar` 加复活（压线不判负 →
答对拉回中线）+ 道具（落后 ≥0.55 且 ≥8s → 答对猛推 0.35），各限 1 次；
`main.gd` 加 `--reward=` / `--reward-url=` / `--ad-policy=` / `--ad-delay=` / `--reward-timeout=` / `--sim-step=`。

**关键顺序坑**：`_tick_playing` 里必须**先问奖励再判胜负** —— 排在 `is_over()` 后面就永远没机会
把「即将判负」翻盘。同理 `_begin_reward()` 要先 `_set_state(REWARD)` 再发请求，因为网关可能**同步**回答。

## 自检 15 组：134 通过 / 0 失败

组 [14]（流程接奖励）最初 3 条 FAIL，**是测试写错了不是产品错**：复活成功后对局继续，
`while flow.state == PLAYING` 循环不会在复活那一刻退出，要跑到第二次压线才结束，届时 state 已是 RESULT。

**GDScript 坑**：lambda 捕获按值，给捕获的**局部变量重新赋值**外面看不到；可变状态要塞进
Dictionary 改内部字段（Array 的 `append` 可以，因为共享同一对象）。

## 框架评审（用户问「有什么建议，针对目前的整个框架」）

通读了 net_protocol / udp_server / player_session / motion_filter / minigame / game_registry /
game_flow / reward_service / 三个网关。**结论：抽象是对的，框架本身不用动**，瓶颈在框架之外。

**两个真正的瓶颈（不是框架问题）**
1. **没有开局入口**。`start_game()` 全项目只被 `main.gd:_maybe_autostart()`（`--autostart` 开发参数）
   和测试调用；`GameRegistry.available_for()` 写好了但没有任何 UI 消费它。
   → 不写大厅，这个项目**在真实场景下永远开不了局**。数据其实都齐了（在线玩家 / 可用玩法 / meta 名字）。
2. **真机手感从未验证**。所有验证都是内置模拟器发的正弦波。
   `MotionFilter` 的 `SWING_THRESHOLD=9.0` / `SWING_COOLDOWN_MS=320` / `TILT_GAIN=2.0` /
   `TILT_DEADZONE=0.06` 全是拍出来的 → 一旦真机跑起来发现手感不对，**按这些数设计的玩法会集体返工**。
   → 建议顺序：**先验手感，再写第二个玩法**。（记忆：手机端必须原生 App，局域网 HTTP 拿不到传感器权限。）

**确认的两处待修（都不致命）**
- `game_flow.gd:79` `drop_player` 用 `_active_count() < current.min_players()` 判「人不够」，
  但拔河额外要求**能均分两队**（`accepts_count` 只认 2/4）。4 人局掉 1 人 → 3 ≥ 2 → 不中止 →
  变成 1v2 继续打。修法：`not current.accepts_count(_active_count())`。
- `game_flow.gd:277` `reward_settled.emit()` 在 `current.apply_reward()` **之前** ——
  监听者收到「奖励到手」时玩法状态还没变（写组 [14] 测试时就被这点绊到，只能改用 state_changed 抓快照）。
  修法：emit 移到 apply_reward 之后，语义变成「奖励已生效」。

**契约上的三处名不副实（会坑后来人）**
- `meta()["inputs"]`：只有 selfcheck 断言它非空，没有任何运行时代码消费 —— 纯文档字段。
- `reward_catalog()`：定义了，无消费者（HUD 不显示可用道具）。
- `result()` 注释写「至少含 winner」，但拔河返回的是 `winner_team` —— 将来做通用结算界面必踩。

**产品判断（关于奖励）**：拔河道具解锁条件是「落后 ≥0.55 且 ≥8 秒」，**可能被策略化成
「故意先落后换一记猛推」**。第二个玩法里就该定下原则：奖励是补偿（快输才给）还是诱惑（随时可换）。

**明确建议现在不要做**：第三个玩法（手感没验）、商店/成就/等级（只有一个玩法时是纯负担）、
服务端/账号（局域网方案的优势就是没有这些）、`--reward=http` 的鉴权（家里局域网不值当）。

**顺手一条**：`UdpServer.TIMEOUT_MS = 3000` 偏紧 —— 手机放下两秒就判离线、槽位置空、人数不够就 abort 整局。
建议 5–8 秒，或加「掉线保留槽位 N 秒」。

## 大厅开局入口（评审后动手的第一步）

**做了什么**：把「玩哪个」变成代码的一部分。此前 `start_game()` 只有 `--autostart` 和测试在调，
真实场景下这个平台**永远开不了局** —— 这是评审里认定的第一瓶颈。

- `core/minigame.gd` 新增 `why_not(n)` 钩子；`TugOfWar` 覆盖它 →「要均分两队，得 2 人或 4 人」。
  **框架不猜原因**：它猜不出这类玩法自己的组队规则，猜出来的提示只会含糊。
- `GameRegistry.evaluate(n)` 新增（每个玩法 ready + reason），`available_for(n)` 改成过滤它。
- `core/lobby.gd` 新建（`class_name Lobby`）：纯逻辑无展示，数据全来自注册表 → **加玩法不用改它**。
- `main.gd` 接线：`_unhandled_input`（用内置 `ui_*` 动作，手柄十字键和电视遥控器都覆盖）、
  `_digit_pressed`（读 `unicode` 不读键码）、`_start_selected`（人数不够只提示不硬开）、
  `_lobby_lines`（`▸` 光标 + 编号 + 人数区间 + 可否开始 + 原因 + desc）。

**顺手改进（不在原计划里，但省事）**：`--autostart` 改成**走大厅同一条路**，
删掉了它自己那份 `players.size() < 2` 的硬编码判据 —— 判据只剩一处，
`--autostart=tug --sim-players=3` 现在会被大厅挡住并说清原因（以前一声不响地失败）。

**踩了两个坑，都值得记**：
1. **`_process` 里 `_refresh_lobby()` 必须排在 `_maybe_autostart()` 前面**。反了的话玩家刚连上那一帧
   菜单还是旧的（0 人），自动开局拿「还差 2 人」去拒绝 —— 症状极具误导性：「5 人也说还差 2 人」。
2. **`Lobby`（新 `class_name`）必须先 `godot --headless --path . --import`**，否则
   `Identifier "Lobby" not declared`。而且那次报错还**卡住不退出**（timeout 124），不是普通报错。

**又发现一个「绿着的坏构建」**：那次 `Lobby` 解析失败导致 `_check_lobby()` 中途崩掉，
但自检照样打印 **「147 通过 / 0 失败」、退出码 0** —— GDScript 运行时错误不抛异常，
只中断当前函数，后面 20 条断言一条都没跑，总量少了却没人发现。
→ 加了哨兵断言 `EXPECTED_MIN`（断言数下限）兜住。**已实测**：把它临时设成 999 会
`[FAIL] 断言总数 ≥ 999（现在 168）` 且退出码 1，恢复 168 后全绿。

**验证**（全部无头，`--reward=off` 的纯大厅部分）：

| 1 | 放弃：《拔河》还差 1 人 |

端到端一局（`--sim-players=2 --sim-step=6 --reward=mock --ad-delay=0`）：
`LOBBY → 倒计时 → 对局中 → 等奖励(道具) → 对局中 → 等奖励(复活) → 对局中 → 结算 → LOBBY`，
结算「左队胜（小明）—— 时间到，占优（本局用了：复活 1 次、道具 1 次）」，
回大厅后菜单重建为「可开」，且**没有再自动开一局**。8800 帧全程 0 丢包。

## 默认名字换成中国神话人物（+ 做成了「默认分配，也能自己改」）

用户要求把内置模拟器的名字池从小明/小红/爸爸… 换成神话人物。追问后澄清了**真实语义**：
「**默认分配一个名字，也可以自己改**」—— 这就不是换个字符串那么简单，而是三条行为：

1. 手机**没输名字** → 大屏从池子里挑一个**还没被占的**给他
2. 手机**报了自己的名字** → 用他自己的，池子完全不参与
3. **想改名** → 重发一次 HELLO 就行（`UdpServer` 覆盖旧名字），**不用加新报文**

**做法**：新建 `core/player_names.gd`（`class_name PlayerNames`）当唯一一份名单 ——
三处共用：`UdpServer` 的兜底、大屏 `--simulate`、单跑 `simulator.tscn`。
之前把池子放在 `simulator.gd` 里、由 `main.gd` 引用的做法**被推翻了**：
现在服务端也要用，池子就不该挂在「模拟器」身上。

- `at(index)`：越界/负数都绕回来（`((i % n) + n) % n`）—— 保证任何整数都给得出名字
- `pick(taken)`：挑第一个没被占的；池子占满就**重用一个默认名**，
  绝不退化成「玩家 7」那种没人认得出的名字（重名至少还能靠颜色和槽位号区分）
- `udp_server._default_name_for(pid)`：**排除自己已有的名字**，所以「重发一次空名 HELLO」
  是幂等的，不会把自己莫名改名 —— 手机端改名字就靠重发 HELLO，这条必须是幂等的，
  否则改坏一次就回不来了
- `main.gd` 删掉自己的 `SIM_NAMES` 常量，直接用 `PlayerNames.at(i)`
- 顺手修掉一个不一致：单独跑 `simulator.tscn` 以前显示「模拟玩家 2」，现在也是神话名

**名单**（9 个，2-4 字，前五个正好是取经五人组）：
孙悟空、猪八戒、沙悟净、唐僧、白龙马、哪吒、二郎神、红孩儿、牛魔王

## 视觉风格定为「扁平卡通风」+ 验证「代码生成 .tscn/.tres」这条路

用户定下**扁平卡通风**，并问「UI 不在代码里 build 还有什么方法」。风格已定，搭法待选。

**用一次性探针实测了「代码生成标准资源」这条路，结论：通。**
（`tools/_poc_ui.gd`，`extends SceneTree`，跑完已删；产物 `tools/_poc/` 也删了）

- `ResourceSaver.save(theme, ".tres")` → OK，919 字节纯文本
- `PackedScene.new().pack(root)` + `ResourceSaver.save(packed, ".tscn")` → OK，1921 字节
- **反过来 `load()` 当普通场景实例化成功**：节点树、主题、卡片数、文字、圆角、底色全都在
  → 产物是**标准资源**，可以交给编辑器继续调 —— 这正是「代码只当一次性脚手架」的前提

**探针顺手抓到一个隐蔽坑（A/B 两版对比出来的）**：
| 写法 | 产物 | 后果 |
| --- | --- | --- |
| `root.theme = Theme.new()`（内存对象） | 内联 `[sub_resource]`，**无** `ext_resource` | 主题被复制进每个场景，**「改一处 .tres 处处生效」失效** |
| `root.theme = load("x.tres")`（自带 resource_path） | `[ext_resource]` 引用，**无**内联 | 主题一份，真正全局可改 |

→ 差别只是**赋给节点前有没有 `load()` 一次**。想全局主题就必须先存盘再 load。
另一个同类坑：子节点忘了设 `owner = root` 就不会进场景（且照样报「保存成功」）。

已把这两条写进 `godot-headless-verification` skill（新增 6.1 节）。

**字体现实约束（前面探针已测）**：系统 Noto Sans CJK 是 19–27MB 的 `.ttc`，
直接嵌进项目太重，要嵌得做子集化（只取用到的字）或换轻量源。
现在靠 `allow_system_fallback = true` + fontconfig 撑着 —— **PC 上没问题，打包 Android 有豆腐块风险**。

**四条路的实际代价**（已交付给用户）：
1. Godot 编辑器手搭 `.tscn` + Theme —— 最正统，反复调视觉最舒服；代价是得开编辑器（用户之前担心手写 tscn 出错，
   但编辑器的场景树/检查器就是为了不手写）
2. **代码生成 `.tscn`/`.tres` 当脚手架** —— 已实测可行；代码从零到有，之后归编辑器
3. GDScript `@tool` 脚本 —— 编辑器里边看边生成；代价是多一套要维护的代码
4. 第三方插件（Dialogic 等）—— 面向对话/演出，不适合当 UI 底座

**我还画了一版扁平卡通风大厅视觉稿**（内联 SVG/HTML，非文件）：深navy 底 + 玩家名彩色药丸

### 卡住的真原因（很值得记）

插件在 `MCP | plugin loaded` 之后报：
```
server start blocked — PermissionError [Errno 13] capability path has an unsafe ancestor:
PosixPath('/home/zm/.config')
```
- 服务端把能力令牌写在 `~/.config/godot-ai/capabilities`，并且**要求每个祖先目录组/其他都不可写**
  （源码 `return info.st_uid in {0, uid} and (mode & 0o022 == 0 or root_sticky_directory)`）
- 这台机器 `~/.config` 是 **0775（组可写）** → `0o775 & 0o022 = 0o020 ≠ 0` → 拒绝 → 服务端退出
- 属主和属组都是 `zm`（同一用户），**去掉组可写零功能影响** → `chmod g-w ~/.config`（0775→0755）解决
- 只改这一个就够：整条链 `/`(755 root)、`/home`(755 root)、`~`(700)、`~/.config`(改后 755) 全通过
- **实测证明**（不只是推理）：直接 import 服务端的 `godot_ai.transport.capability`，
  调 `write_capabilities()` 写入成功（目录 0700 / 文件 0600），读回正常，探针文件与空目录已清理

**顺带排掉的两个次生风险**（都实测过，都不是问题）
- 编辑器是从桌面启动的，怕 PATH 里没 `~/.local/bin` 找不到 uvx → 读 `/proc/<pid>/environ` 确认
  `PATH=/home/zm/.local/bin:...`，uvx 找得到
- `XDG_CONFIG_HOME` 未设 → 正好回退到刚修好的 `$HOME/.config`

**失败详情在哪**：`~/.local/share/godot/app_userdata/HomeGame Screen/godot_ai_server_startup.json`
（一个 JSON，含 pid / error / message / hint）。排查顺序就是它 → 端口 8000/9500 → `ps` 有无 python 服务端。

**插件不会无限重试**：报告显示它在 11:38:47 又试过一次（新 pid）后就不再自己起来；
改完权限仍需在 `项目设置 → 插件` 把 Godot AI 关掉再打开（等价于 dock 里的 Reload/Restart）才会重来。

**注意**：用户当时**已经开着一个编辑器**（PID 536488，已跑 2h40m），是在装插件之前启动的。

位移**不进布局**、不挤动旁边的卡。见 `hud.gd:_tile_wrap()`。

叫 `game_tile_0_wrap` 会被当成第二张磁贴（自检报「磁贴 3」）。现在叫 `wrap_of_<原名>`。

### 补修：磁贴圆角被封面「顶出去」（用户实拍发现）

用户报「**游戏块圆角出去了**」。根因：磁贴是 `PanelContainer` + 圆角 `StyleBoxFlat`
（`TILE_RADIUS = 28`），但封面 `plate` 是个**方角 `Panel`、铺满整块磁贴** ——
`StyleBoxFlat` 的圆角**只管自己的底和边，管不住子节点**，于是封面的方角正好盖在磁贴圆角上，
色块从卡片圆角处凸出来（上边两个角最明显，下边两个被白底名字区挡着看不见）。

修法（`ui_kit.gd:tile()`）：**`p.clip_children = Control.CLIP_CHILDREN_AND_DRAW`**
（= 2）。裁剪会跟随 StyleBox 的圆角，封面自然沿卡片弧度收边，通栏效果保留但不越界。

- ⚠️ **必须用 `AND_DRAW` 不能用 `ONLY`** —— `ONLY` 会把磁贴自己的白底和描边一起裁掉，
  卡片就没了
- **空位卡不用修**：它的 panel 底色是 `Color(0,0,0,0)`（全透明），虚线框是自己画的圆角矩形
- **`card()` 也不用修**：它没把 `content_margin` 归零，子节点本来就落在圆角内
- 实拍对比确认（`cmp_before_*.png` / `cmp_after_*.png`）：修复前红蓝封面把方角顶在圆角外，
  修复后沿着圆角收边
- **通用教训：Godot 里只要「圆角容器 + 铺满的子色块」，就必须开 `clip_children`。**
  StyleBox 的圆角是画给自己看的，不会约束子节点

### 补修 2：磁贴内边距漏了 ×k 换算（用户实拍发现「内边距太挤了」）

用户报「**内边距太挤了**」。根因：`TILE_PAD` **直接照抄了设计稿的 CSS 值 18**，
漏了 ×1.532 换算。同一份令牌里 `RADIUS`（18→28）和 `TILE_GAP`（22→34）都换算对了，
**只有内边距按原值来** —— 于是「卡与卡之间的空隙」比「卡内部的留白」大得多，比例反了。

| 项 | 设计稿 CSS | 应有（×k） | 修复前 | 修复后 |
|---|---|---|---|---|
| 圆角 | 18 | 27.6 | **28** ✅ | 28 |
| 网格 gap | 22 | 33.7 | **34** ✅ | 34 |
| 内边距 左右 | 18 | 27.6 | ~~18~~ ❌ | **28** |
| 内边距 下 | 18 | 27.6 | ~~18~~ ❌ | **28** |
| 内边距 上 | 16 | 24.5 | ~~14~~ ❌ | **25**（新增 `TILE_PAD_TOP`） |

**已实拍确认**：修复后 `margins L=28 T=25 B=28`，名字和徽章不再顶着卡片边缘。

**通用教训：设计稿上的 CSS 数值，凡是「空间量」（padding/margin/gap/height/radius）
一律要 ×k 换算，不能照抄。** 字号和描边宽度反而**不该**换算（字号自成一套刻度、
描边在 1080 基准上本来就是设计意图）。这里错就错在把「空间量」和「不换算项」混在一起处理了。
