# 手机端 ↔ 大屏 通信协议（v2）

> **权威来源**：`screen/scripts/net/net_protocol.gd`。
> 本文是给**手机端实现者**看的对接文档。**改协议必须同步改本文并 +1 `VERSION`。**
>
> 手机端**不调用任何 Godot 接口** —— Godot 是游戏引擎，不是服务端，没有 RPC 入口。
> 两端唯一的契约是**字节格式**。手机端要做的就是：读传感器 → 按本文编码 → UDP 扔给大屏。

---

## 0. 一句话说清两端边界

```
手机 App                                     大屏（Godot）
─────────                                   ─────────────
读传感器（平台 API）                          UdpServer 收包
   ↓                                            ↓
按本协议编码成字节（无 Godot 依赖）    ←UDP→   NetProtocol.decode_*()
   ↓                                         MotionFilter 滤波/判动作
UDP 发送到 大屏IP:8910                          ↓
                                          玩法层读 jump()/tilt()
```

**手机端需要实现的只有左列三步。** 大屏那边的解码、滤波、判定全部现成。

---

## 1. 通用头（10 字节，**全部小端**）

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | u8 | `magic` | 固定 `0xA7`。不对就整包丢弃 |
| 1 | u8 | `version` | 当前 `2`。**不匹配直接丢** |
| 2 | u8 | `type` | 见下表 |
| 3 | u8 | `pad` | 保留，**固定 0** |
| 4 | u16 | `player_id` | 玩家编号，1 起。同一局内不能重复 |
| 6 | u32 | `seq` | 递增序号，从 0 开始。用于丢包统计 |
| | | | **合计 10 字节** |

### 报文类型

| type | 名称 | 方向 | 总长 | 用途 |
|---|---|---|---|---|
| `0` | `DATA` | 手机→大屏 | **40 B** | 传感器数据，60Hz 持续发 |
| `1` | `HELLO` | 手机→大屏 | 11–35 B | 报名（带名字），进场发一次 |
| `2` | `BYE` | 手机→大屏 | 10 B | 礼貌退出，可省 |
| `128` | `FULL` | 大屏→手机 | 10 B | **房间已满**，别傻等 |

---

## 2. DATA（type=0）—— 最核心的包

头之后紧跟：

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 10 | f32 | `gyro.x` | 角速度，rad/s |
| 14 | f32 | `gyro.y` | |
| 18 | f32 | `gyro.z` | |
| 22 | f32 | `accel.x` | 加速度，**m/s²（含重力分量）** |
| 26 | f32 | `accel.y` | **向上为正** —— 「蹦」靠这个判定 |
| 30 | f32 | `accel.z` | |
| 34 | u16 | `buttons` | 按键位掩码；**不用就发 0** |
| 36 | u32 | `timestamp_ms` | 手机本地毫秒时间戳（仅调试用） |
| | | | **合计 40 字节** |

### 静态握持时的期望值

手机**竖持**、屏幕朝向自己、静止不动：

```
gyro  ≈ (0, 0, 0)
accel ≈ (0, +9.81, 0)      ← y 轴上是重力，向上为正
```

⚠️ **各平台原生坐标轴与这个约定不一致，必须转换**（见第 5 节）。

---

## 3. HELLO（type=1）—— 报名

头之后：

| 偏移 | 类型 | 字段 |
|---|---|---|
| 10 | u8 | `name_len` | 名字的 UTF-8 字节数 |
| 11 | bytes | `name` | UTF-8 编码，**≤ 24 字节** |

### 名字截断规则（**容易写错**）

- 上限是 **24 字节**，不是 24 个字符。
- **必须按「字符」回退，不能按字节切**：一个汉字占 3 字节，从中间切开会产生非法 UTF-8，大屏解出来是乱码。
- 正确做法：逐字符累加，超过 24 字节就停。即「能放几个汉字放几个」。

示例（Go/Java/Kotlin 都类似）：
```
"孙悟空"        → 9 字节，OK
"一二三四五六七八" → 24 字节，刚好
"一二三四五六七八九" → 27 字节，必须截成前 8 个字
```

### 三个行为约定

| 情况 | 行为 |
|---|---|
| **不报名**（不发 HELLO 就发 DATA） | 大屏会**自动分配**一个名字（孙悟空、猪八戒…池子里挑未占用的） |
| **报了就用自己的** | HELLO 里的名字优先 |
| **改名** | **重发一次 HELLO** 即可，不需要新报文类型 |

## 4. 字节序陷阱（**最高危**）

协议**全部小端**（Little-Endian），因为 Godot 的 `StreamPeerBuffer` 设了 `big_endian = false`。

**各平台默认值不同，写错不会报错，只会让数值变成天文数字或 NaN：**

| 平台 | 默认字节序 | 必须做的 |
|---|---|---|
| Kotlin `ByteBuffer` | **大端** ⚠️ | `ByteBuffer.allocate(40).order(ByteOrder.LITTLE_ENDIAN)` |
| Java `ByteBuffer` | **大端** ⚠️ | 同上 |
| Dart `ByteData` | 方法显式指定 | `setFloat32(offset, v, Endian.little)` |
| C/C++ | 看机器 | 桌面/手机基本都是小端，但别假设 |
| ArkTS `DataView` | 看方法 | `setFloat32(offset, v, true)` ← 第三参 `true` = 小端 |

**自测方法**：把 `accel.y = 9.81`（float32 = `0x411CF5C3`）编码后，字节应该是
`C3 F5 1C 41`（小端）。如果你的输出是 `41 1C F5 C3`，就是字节序写反了。

---

## 5. 坐标系对齐（**第二高危**）

协议约定的是 **Android 设备坐标系**：

```
x → 屏幕向右
y → 屏幕向上          ← 「蹦」判定依赖这个方向
z → 垂直屏幕向外（朝用户）
```

### 各平台要做的转换

**Android**：`SensorManager` 给的**就是这个约定**，直接用。✅

**鸿蒙 `@ohos.sensor`**：给的也是标准设备坐标系，但**手机横竖屏旋转时轴会变**。
需要读 `display.getRotation()` 并在软件里把轴转回来，否则玩家转动手机后方向就乱了。

**iOS（如果以后要做）**：`CoreMotion` 用的轴与 Android 不同，需要自己做映射。

### 兜底：零点校准

大屏侧 `MotionFilter.calibrate()` 会把「玩家站定那一刻的读数」当作零点。
所以**玩家举着手机的姿势差异不影响判定**，但**轴方向映射错了，校准也救不回来**。

## 6. 验收清单

手机端实现完后，按这个顺序验证（**从易到难**）：

| # | 验证项 | 方法 | 通过标准 |
|---|---|---|---|
| 1 | 字节序 | 编码 `accel.y=9.81`，看第 26 字节 | 是 `C3`（不是 `41`） |
| 2 | 包长 | 编码一个 DATA 包 | 正好 40 字节 |
| 3 | magic/version | 看第 0、1 字节 | `A7`、`02` |
| 4 | 大屏能认出 | 大屏跑 `--simulate` 后，手机发 HELLO | 大屏日志出现名额分配、HUD 席位点亮 |
| 5 | 数据在流 | 手机发 DATA | 大屏日志「收包 N」持续增长、丢包率低 |
| 6 | 方向对 | 手机**向上甩** | 大屏日志的 `jump` 值冲高（不是 0） |
| 7 | 蹦能推绳 | 进拔河局，快速连续蹦 | 绳子往自己队方向走 |

**第 6 项是分水岭** —— 它一次验证了「坐标系正确 + 字节序正确 + 包格式正确」三件事。

### 第 6 项的常见失败症状

| 症状 | 大概率原因 |
|---|---|
| `jump` 一直是 0 | 字节序写反（数值变 NaN/极大）／坐标轴映射错 |
| **向下甩**才冲高 | y 轴符号反了 |
| 冲高但微弱 | 单位不是 m/s²（可能用了 g，差 9.8 倍） |
| 时有时无 | 发送频率太低（协议按 60Hz 设计，低于 20Hz 会丢掉冲高瞬间） |

## 7. 发送节奏

- **HELLO**：进场时发一次；改名时重发
- **DATA**：**60 Hz**（每 16.7ms 一包）。这是设计值。
  - 低于 ~20Hz：「蹦」的冲高瞬间会被漏掉，手感顿
  - 不必高于 60Hz：手机传感器本身大多就 50–100Hz，再高只是浪费电
- **BYE**：退出时发（可省，不发就让大屏等 3 秒超时）
- **seq**：每发一包 +1（u32 溢出回绕没关系）

### 收到 FULL（type=128）怎么办

大屏满员时会回一包 `FULL`。手机应：**静默 3 秒后重发 HELLO**（模拟器就是这个行为），
并在界面上提示「房间已满，重试中」。**不要疯狂重连**。

## 8. 参考实现

大屏仓库里有两个现成参照物，**手机端就是它们的等价重写**：

| 文件 | 说明 |
|---|---|
| `screen/scripts/sim/simulator.gd` | **「真实手机端的第一版实现」**（代码注释原话）。业务逻辑可直接照搬 |
| `screen/scripts/net/net_protocol.gd` | 协议的**权威定义**，也是解码端 |

模拟器已经做了：60Hz 造波形 → `encode_data()` → UDP 发到 `target_host:8910` → 先进场发 HELLO → 退出发 BYE。
**手机端要做的就是把这份 GDScript 用 Kotlin/ArkTS/Dart 重写一遍。**
